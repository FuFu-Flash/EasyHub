为什么做 EasyHub

GitHub 很好用，但门槛不该这么高

命令行看不懂

add、commit、merge、rebase，一连串概念；一个报错信息就足以让人卡住，更不敢随便按回车。

选个文件夹、写句话、点一下就发布

官方客户端只管 Git

GitHub Desktop 聚焦提交与分支，不浏览 Issues、不发 Release；项目还得先理解克隆和仓库结构。

项目、问题、发布、下载收进一个窗口

网页操作零散

看项目、下载 ZIP、回复问题、查历史版本，要在浏览器多个页面来回跳，下载断了也不知道进度。

桌面端统一完成，下载带速度与剩余时间
核心特性

一个窗口，覆盖日常用到的 GitHub 操作

未登录时所有功能在演示模式中即可完整体验，数据只存在于当前窗口；GitHub 登录后切换为真实项目，访问令牌仅保存在 Windows 凭证管理器，全程直连、无 EasyHub 服务器。

演示 / 真实双模式

未登录也能新建项目、发布更新、回复问题，只修改窗口内的演示数据并在重启后复原；登录后同样的界面操作真实 GitHub。

本地文件夹发布源码

选择任意文件夹即可识别为项目；独立 Worker 扫描新增、修改、删除、重命名的文件，遵守 .gitignore、避开依赖目录，变化时防抖复检。基于 isomorphic-git，无需安装 Git。

冲突安全处理

发布前先检查云端版本：可安全衔接的更新自动先获取；双方改动同一文件时，逐个查看并选择保留版本。复杂历史和未完成写入会阻止自动发布，绝不强制覆盖。

问题全流程管理

创建问题、回复评论、关闭与重新打开；问题列表按项目分组，从全局进入默认收起、从项目详情进入自动展开对应项目。

发布新版本 Release

正式版、Alpha、Beta 三种类型，自动建议并续号版本名；可插入链接与图片、选择多个下载文件，按 GitHub 公开限制校验（单文件小于 2 GiB、每版最多 1000 个、不可同名）。

真实 Release 上传规划中，当前为演示流程

公开内容翻译

一键统一翻译项目简介、README、问题与 Release 描述；README 按段落随滚动逐步翻译。私有项目不发送给第三方，项目名、版本号、文件名以占位符保护，译文本地缓存。

使用流程

四步，把本地改动发布到 GitHub

整个流程不需要命令行，也不需要事先理解分支、暂存区等概念。

步骤 01

选择本地文件夹

添加电脑上已有的文件夹并识别为项目，或把 GitHub 上的云端项目下载到指定位置。

步骤 02

自动检查改动

独立 Worker 扫描文件的新增、修改与删除，遵守 .gitignore 并避开常见依赖目录。

步骤 03

写说明、处理冲突

用一句话说明本次更新；若云端也有改动，逐文件对比并选择要保留的版本。

步骤 04

一键发布源码

自动先拉取可衔接的远端更新，再把本地改动安全同步到 GitHub，完成后可查看历史版本。

桌面端"全功能 GitHub 客户端"仍是空白生态位

官方 GitHub Desktop 主动聚焦 Git 工作流；DevHub、Gitify 只切通知场景；冲平台全覆盖的 OctoPunk 尚未发布且为闭源。EasyHub 把平台浏览、本地源码发布与中文零门槛合进同一个窗口，并提供无需登录的演示模式。

一句话定位

EasyHub ≈ 桌面端的 ForkHub 思路，加上 GitHub Desktop 的本地发布能力，再叠加免安装 Git、中英双语与公开内容翻译。以上对比基于各项目 2026 年 9 月的公开资料，能力会随版本变化。

开始使用

两种方式运行 EasyHub

Windows 便携版 EXE

在 Windows 上执行打包命令，得到单文件便携版，双击即可运行、无需安装 Git：

pnpm package:win

输出位置：apps/desktop/release/EasyHub-0.1.0-portable.exe。未使用商业代码签名，首次运行 Windows 可能提示"未知发布者"。

从源码运行

环境要求：

  • Windows 系统
  • Node.js 22 或更高
  • pnpm 11 或更高
# 安装依赖并启动
pnpm install
pnpm dev

检查与构建

交付前可运行完整检查，另有 UI 冒烟测试 pnpm test:ui：

pnpm typecheck
pnpm lint
pnpm test
pnpm build
